A Go map that never grows still changes

2026-10-12 · Kit Wickham

Take a Go map with a fixed number of keys and churn it: delete a random key, insert a new one, over and over. The key count never changes. On Go 1.27.1, two things happen anyway. For about two map sizes in five, the map doubles its memory and stays doubled. And at all three sizes I timed, lookups of keys that aren't in the map got 2.5 to 4 times slower, which is slower than the same churned map on Go 1.23. Both come from how Go's Swiss-table maps handle deleted slots. A fix that the runtime source itself suggests helps the memory but costs 17–45% more time per churn operation.

How deletes work

Since Go 1.24, maps are Swiss tables. Slots sit in groups of eight, each group with eight control bytes. A lookup hashes the key, walks a probe sequence of groups, and stops at the first group that has an empty slot: the key would have been put there, so it isn't in the map. That stop rule is why a delete can't always just empty a slot. If the group is full, some other key may have probed past it, and emptying a slot would make that key unreachable. So the slot gets a tombstone: not a key, but not empty either.

A large Go map isn't one table. It's a directory of tables of at most 1024 slots each. A full table splits into two, and the directory doubles when it has to. Tables never merge. And there's no step that clears tombstones in place: a comment in rehash says Swiss tables usually do that, but it's unclear how to do it without breaking iteration order, so the table grows instead.

That used to make churned maps grow repeatedly (Go issue #70886). The fix (CL 640955) added pruneTombstones. Reading it in the current source: when a table runs out of room, it first clears the tombstones that no live key's probe path crosses, but only if that frees at least 10% of the table. Otherwise the table grows or splits as before. The maintainers' reasoning in the issue was that tombstone-driven growth is logarithmic: each doubling makes the next one harder.

Measuring it

I read the map's internals from outside with unsafe copies of the runtime's structs (checking that the tables' live counts add up to len), so I could count tables, slots and tombstones directly. The workload is a map[uint64]uint64 with random keys. One turnover is n delete-plus-insert operations on a map of n keys. For comparison, I built a fresh map from the same final keys. Everything ran on linux/arm64.

Across 50 sizes from 4,096 to 3.9 million keys (3 seeds each, 40 turnovers), 20 sizes ended with twice the slots of a fresh map, and none went past twice. What decides it is how full the fresh map is. Go tables fill to at most 7/8 before growing, so depending on n, a fresh map is anywhere from about 44% to 78% full. Running longer:

So the growth does stop after one doubling, as the maintainers expected. But "one doubling" applies to every map that was more than about 60% full when it was built, and that's a lot of sizes. Counting how pruning went in a patched runtime at 101,955 keys (76% full): of the tombstones present when pruning gave up, only 31% were removable. The rest sat on some live key's probe path.

Old Go maps weren't better on memory. The same churn with Go 1.23's bucket maps used 1.5 to 1.9 times the bytes of a fresh map at every size I tried, and churned bytes per key were 41–70 on Go 1.23 against 34–53 on Go 1.27. On memory, Swiss tables come out ahead or roughly even.

Missing keys get slow

The bigger effect is on lookups for keys that aren't there. A churned map ends up full of tombstones, and a miss can only stop at a group with a truly empty slot. At 134,836 keys, a size where the map didn't grow at all, 40 turnovers left about 59,000 tombstones, and the share of groups with an empty slot fell from 94% to 47%. Nanoseconds per lookup:

Ranges are over three seeds; the Go 1.23 column is one run. Fresh, the two versions are close (Go 1.27 is faster at two of the sizes and slower at 90,000). After churn, Go 1.27 is about twice as slow. Hits barely changed at the two smaller sizes (4.2–4.9 ns either way) and went from about 11 to 16 ns at 1.45 million keys, where the churned map is twice as big.

One practical catch: maps.Clone doesn't clean anything. It copies the tables as they are, tombstones included; the clone of the churned 134,836-key map had the same tombstone count and the same 18.5 ns misses. Copying the keys into a new map with a range loop gives a clean map. If a long-lived map takes a lot of deletes and you look up absent keys often (a cache in front of something, a set of seen IDs), rebuilding it now and then is cheap insurance.

The fix the source suggests

The same comment in rehash offers an alternative: rebuild the table into a new allocation of the same size, which drops tombstones without the iteration problem. I tried that through a build overlay: when a table runs out of room and its live keys are at most a threshold fraction of its slots, rebuild it at the same size instead of growing. A toggle in one binary switched it on and off.

At a threshold of 840/1024 slots, memory stayed flat for 400 turnovers on maps up to about 70% full. Above that it only delayed the doubling: tables keep splitting near the limit because each table's key count wanders under random churn, and tables never merge. Abseil's own cutoff of 25/32 held only to about 67%. The cost, timed serially over 200 turnovers:

It halves the memory up to about 69% load (about a third less at 73%) and does almost nothing for misses: at 90,000 keys, misses were 17.7 ns against 19.7 stock, because tombstones build up again between rebuilds. So it's a real tradeoff, not a free fix, and keeping things simple looks like a reasonable call. The miss slowdown is the part I'd want fixed, and a same-size rebuild alone doesn't do it.

Limits

One key type (uint64 to uint64), uniformly random keys and deletes, one machine. Real workloads that delete mostly old keys, or that grow and shrink, may behave differently. The patch is a measurement aid, not a proposal: I didn't run Go's tests against it or look at iteration while it runs. I didn't compare with Abseil itself under the same churn.
