In a VM on the M6, huge pages stop at the host's 16K

2026-10-14 · Kit Wickham

Inside an arm64 Linux VM on an Apple M6 Mac, I chased random pointers through a 1 GB buffer backed by each page size the guest kernel offers. With ordinary 4 KB pages a load took 109 ns. With 2 MB pages it took 94 ns, and 32 MB or 1 GB pages were no better than 2 MB. The same code on macOS itself, with its 16 KB pages, took 87 ns. A second test that stresses only address translation shows why: however big the guest's pages are, the CPU behaves as if it caches translations at most 16 KB at a time, which is also the host's page size and, as far as I can tell, the size the hypervisor maps the guest's memory in.

The setup

The guest is Linux 6.18 with 4 KB base pages and no transparent huge pages, so huge pages come from hugetlbfs pools reserved at boot: 64 KB (16 small pages marked with the arm64 "contiguous" hint), 2 MB, 32 MB (another contiguous size) and 1 GB. A small Rust program maps a buffer with each size, fills it, links its 128-byte lines into one random cycle and follows it: every load depends on the one before, so the time per load is the full memory latency including any page-table walk. It also measures eight independent random load streams, which is closer to what a hash table under heavy load sees. The host run is the same program built for macOS.

This chip has fast and slow cores and the VM's single CPU moves between them. So each measurement is 40 short chunks, each with a clock check before and after, and only chunks that ran on a fast core count. Eight fresh VMs ran three shuffled rounds each, with a host run after each VM, so most cells in the first table are medians of 21 or 22.

At 128 MB and above the quartiles of each cell are within about 2 ns of the median. At 64 MB, just past the last cache level, they spread by up to 7 ns, so read that row loosely; I left out 32 MB, where the spread was larger than the differences. Three things stand out. Going from 4 KB to 2 MB pages in the guest saves 15 ns per load at 1 GB, 13%, and 10% on the independent streams. The 64 KB contiguous pages save nothing measurable, so the core gets no benefit from that hint here. And past 2 MB nothing changes, yet even with 1 GB pages the guest stays 5% (at 128 MB) to 9% (at 1 GB) behind the host.

A test of translation alone

A dependent load over a gigabyte mostly measures DRAM, so the page-table part is a small slice of the total. To isolate it, I ran a second set (six fresh VMs, three rounds each, medians of 17 or 18) with the pointer chain spread thinly: one 128-byte line in every 16 KB, at a varying offset so the lines don't pile into the same cache sets. A 1 GB span then holds only 8 MB of data, which fits in cache, but it touches 65,536 different 16 KB pages. A plain chase over 8 MB costs about 6.8 ns per load on the host and with huge guest pages (7.1 ns with 4 KB guest pages), so anything above that is the cost of finding translations.

If the guest's 1 GB page became one 1 GB translation in the CPU's TLB, the whole span would be a single entry and the cost would fall to the 6.8 ns of the plain 8 MB chase. Even 2 MB pages would need only 512 entries. Instead the guest with 1 GB pages is at 19.6 ns, well above the host's 11.3 ns with ordinary 16 KB pages. At a 64 MB span the guest's page size makes almost no difference (14.4 to 15.3 ns) while the host pays half that. The guest acts as if every translation covers at most 16 KB, and as if each miss costs about twice what it costs the host.

That fits how arm64 virtualization works. A guest address goes through two translations: the guest's own page tables, then the hypervisor's "stage 2" tables that map guest memory onto host memory. A cached translation can only be as large as the smaller of the two mappings. Apple's Hypervisor framework now lets a VM set its memory granule down to 4 KB; asking the framework for its default on this Mac (hv_vm_config_get_default_ipa_granule) returns 16 KB, the same as the host's own pages. Since 1 GB guest pages still behave like 16 KB, the guest's memory looks like it is mapped page by page at stage 2, not in larger blocks. I can't tell that apart from the TLB simply not keeping larger combined entries; either way the effect is the same.

Why do 2 MB guest pages still help, if they don't make the cached translations bigger? Because a miss is cheaper. In a VM, every step of the guest's page-table walk is itself a guest address that needs a stage-2 translation, so the walk costs many more memory references than on bare metal; for four guest levels and four host levels it can be up to 24. A 2 MB page removes one level of the guest walk and with it a whole stage-2 lookup. Bigger pages only remove upper levels, which the walker probably has cached already; that would explain why 32 MB and 1 GB add nothing.

What to take from it

For memory-heavy work in a Linux VM on Apple silicon, 2 MB huge pages are worth turning on: 8 to 13% on random access over 256 MB to 1 GB buffers, and 1 GB pages add nothing over that. Don't expect the gains huge pages give on bare metal, where one 1 GB page covers a whole gigabyte with a single TLB entry. In this VM the translation limit is the host's 16 KB, and on buffers of 128 MB and up the guest stays 5 to 9% behind native whatever page size it uses. The 64 KB contiguous size bought nothing here.

Method: Rust with the libc crate, built static for aarch64; Linux 6.18.35 guest with one CPU and 6 GB of memory, a fresh VM per run; hugetlbfs pools via /sys/kernel/mm/hugepages and MAP_HUGETLB with the size encoded in the flags. Each value is the median over fast-core chunks of 200,000 loads; core tier by an add-chain clock check. 2,013 dense and 1,933 sparse measurements, 14 dropped for too few fast-core chunks. The stage-2 default was read with hv_vm_config_get_default_ipa_granule; that the VM I used keeps the default is my inference.
